## Раунд 2: глубокое тестирование редактирования (чат / карточка / лорбук)

### BUG-3 (высокий): пустой/несработавший лорбук невидим для модели → Copilot создаёт новый вместо него — ✅ ИСПРАВЛЕНО
- **Фикс:** `buildLBAIInstructions` теперь строит `{{active_lorebooks}}` из `getActiveLorebookNames()` (глобальные + персонажа + чата + персоны, минус исключённые), а не из записей, попавших в контекст.
- **Живой ретест:** пустой `QA-EMPTY`, привязанный к чату, появился в промпте: `active lorebooks: "0000тулзы", "Eldoria", "QA-EMPTY"`.
- **Симптом (как у пользователя):** «копилот не видит пустой лорбук без записей, привязанный к чату — предлагает создать новый».
- **Корневая причина:** `buildLBAIInstructions` (feature-lorebook-engine.js:397) строит список `{{active_lorebooks}}` из `lastActiveEntries` — т.е. только книг, из которых записи реально попали в контекст (по ключам/константе/ручному выбору). Пустая книга или книга без сработавших ключей в список не попадает.
- **Живое воспроизведение:** создан пустой лорбук `QA-EMPTY`, привязан к чату через `chatMetadata.world_info`. В промпте: `active lorebooks: "0000тулзы", "DARK CHURCH ✝︎ Damien"` — QA-EMPTY отсутствует, `QA-EMPTY` в системном промпте не встречается вообще.
- **Усугубление в apply-пути:** `applyLBChanges` (feature-lorebook-ui.js:175-186): если модель указала `worldName`, которого нет среди активных, вызывается `bindNewLorebookToCharacter` → **молча создаётся новый лорбук и привязывается к персонажу** (не к чату). То есть «предлагает создать новый лорбук» на деле = реально создаёт новый.
- **Что работает:** дропдаун выбора книги в карточке правки содержит QA-EMPTY (там используется `getActiveLorebookNames()`, который чатовую книгу видит), и `add` в пустую книгу применяется корректно (запись создана с uid 1).
- **Рекомендация:** в `buildLBAIInstructions` подставлять в `{{active_lorebooks}}` результат `getActiveLorebookNames()` (за вычетом excluded), а не только книги с активными записями; либо дополнительно перечислять «активные, но пустые/несработавшие» книги отдельной строкой.

### BUG-4 (средний): правки чата помечаются «применено», когда якорь не совпал (записи «не редактируются») — ✅ ИСПРАВЛЕНО
- **Фикс:** `applyChatChanges` возвращает массив фактически применённых изменений; UI (per-item и «Применить всё») помечает `applied` только их, несработавшие остаются pending.
- **Регрессионный тест:** `tests/chat-edit-apply.test.js` (3 кейса: валидный якорь, битый якорь, delete с несуществующим индексом). Весь сьют: 138/138.
- **Живой ретест:** патч с несуществующим якорем → «Применить всё» → сообщение не изменено, элемент остался «1 ожидает».
- **Симптом (как у пользователя):** «иногда записи просто не редактируются».
- **Корневая причина:** в `applyChatChanges` (feature-chatedit-engine.js:331-339, 369-379) при несовпадении якоря выполняется `toastr.warning` + `continue` **без выброса исключения**. А UI (feature-chatedit-ui.js:370-379 per-item и 644-656 apply-all) помечает элемент `applied` ДО вызова и откатывает только при брошенном исключении. Итог: сообщение в чате не изменилось, а в UI — «применено» и в историю оно не пишется (не попадает в successLog).
- **В лорбуке этой проблемы нет:** и per-item, и apply-all сверяются с возвращённым массивом `applied[]` и оставляют несработавшее в pending (feature-lorebook-ui.js:614-618, 799-810). В LB невалидный якорь вообще блокирует кнопку ✓ клиентской валидацией (проверено live: ⚠ «ANCHOR не найден», кнопка disabled).
- **Рекомендация:** `applyChatChanges` должен возвращать список фактически применённых изменений (как `applyLBChanges`), а UI — сверяться с ним; либо бросать исключение при полном провале.
